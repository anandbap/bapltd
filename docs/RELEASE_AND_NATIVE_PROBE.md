# Release integrity and native reporting probe

Implemented P1b-01/02, October 31, 2026 (local time). These are qualification tools, not a completed corporate SSO/Windows/20-person pilot acceptance.

## Matched release bundle

Wheel builds now write `bap/bin/<platform>/bap-release.json` after staging the edge, interceptor, Claude starter scripts, launcher engine on Windows, and installer/startup/doctor/release-checker modules. The manifest records component sizes/SHA-256 hashes, packaging commit, and available Go embedded build identities. Its release ID identifies the exact manifest contents, not merely a version label.

For a controlled pilot, install the matching approved package using `bap install ... --require-release-manifest`. This requires a complete manifest and consistent known, non-dirty build identities. Checks run **before** stopping/replacing an existing installation, and again against installed files; a locked/stale component cannot silently pass the upgrade. The latter check reports failure rather than claiming a successful installation. Atomic rollback of an interrupted multi-file upgrade is not implemented by this check.

Legacy/ad-hoc installations without the flag remain supported but unqualified when a manifest is absent or build identity is unknown. A present malformed/mismatched manifest fails integrity checks. `bap doctor` recomputes current file hashes; `daemon status --json` reports the last installation-time provenance snapshot and explicitly distinguishes it from a fresh inspection.

**Trust boundary:** a hash manifest is not a publisher signature or attestation. Consistent embedded build labels are not an independent proof of publisher origin. Use the approved package drop's external trust anchor/signature/hash-verification process. Doctor marks publisher authenticity as not checked. Enterprise signing, centrally approved bundle policy and clean release qualification remain open; no signing keys or credentials were accessed/generated by this work. A dirty development checkout can test functionality without qualifying as a clean pilot release.

## Native probe: operator flow

Use matching updated control-plane, edge and interceptor builds on a disposable test workstation/fixture repository. Complete install/login first. Neither command below installs hooks, approves native-client permission prompts, grants execution authority, unfreezes anything or changes capture policy.

1. Run `bapedge onboarding begin`. It saves a random, 15-minute local probe and prints a harmless synthetic prompt containing `BAP-ONBOARDING-<probe-id>`.
2. Start a **new** supported Claude session after beginning the probe. Paste the printed prompt exactly. Use the native client's normal approval process, and let it request `git status` in the fixture repository and finish its response.
3. Run `bapedge onboarding check --require`. The command uses the master enrolled destination/credential. No admin token is needed on the workstation.

`reporting_probe_observed` requires all of the following:

- Fresh, ordered local SessionStart → UserPromptSubmit → PreToolUse → Stop callbacks after the probe began.
- Matching opaque session references across all four callbacks and the probe identifier on the prompt callback. Raw native session identifiers are not copied into callback health files.
- A centrally retained native-hook prompt record from a Claude session **owned by that authenticated workstation**, matching the synthetic marker or the digest of the exact public synthetic prompt. Hash-only matching supports existing prompt-text capture opt-out; no private prompt text is required by the query/response.
- A matching session's allowed `git status` policy record in the probe interval and no current session/workstation restriction. A denial remains a denial and does not qualify the allowed reference workflow.

Missing delivery, rejected identity, expiry, SDK-only prompts, different session references, missing callbacks or policy denial yield partial/expired results; `--require` exits nonzero. Do not infer the cause as refused approval. Lower-layer reporting and local enforcement continue independently of probe status. Re-run a fresh probe if the operator pasted the marker into multiple sessions or the evidence window was exceeded.

There is one active probe per local profile. Concurrent sessions can replace per-phase health markers and yield a partial result; qualify the reference workflow sequentially rather than treating mixed-session callbacks as one successful probe.

## Exact scope and limits

`GET /api/v1/onboarding/probe` requires a valid workstation proof and returns only owned probe metadata/opaque references, never prompts, raw session IDs, user identities, full commands or other workstation details. The interval is at most 15 minutes and the audit search is bounded to the latest 1,000 records; missing old records remain unknown. Data depends on current stores/recovery; P3 authoritative persistence is still pending.

A reported policy allowance is not a verified execution result. Both endpoint and CLI keep `execution_success_verified: false`. Locally produced callback records and authenticated self-reported audit evidence are not tamper-resistant proof that the real Claude binary executed the callback. An operator must still validate the real client/approval flow. The probe reports a correlated observation, not regulatory compliance, completed work, employee productivity or full pilot readiness.

Automated verification covers manifest mismatches/strict preflight, changed components, platform/component allowlists, unknown/dirty identities, metadata privacy, owner scoping, capture-disabled public digests, callback ordering/session mismatches, expiry and real edge-CLI ↔ control-plane protocol traffic with **synthetic native markers**. Those fixtures do not approve hooks or qualify real Claude/corporate IdP integration.

Still pending: signed/centrally approved release trust, actual OS logon/reboot and clean-user upgrade tests, real supported Claude/native approval/capture probes, corporate SSO verification, expected 20-person roster/reporting windows, durable history and P2 cross-layer operation identity.
